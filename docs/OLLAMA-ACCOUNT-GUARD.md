# Ollama local-account guard

**Candidate: not released or installed.** Exact-source kernel tests and
administrator installation acceptance are separate gates. This document does
not authorize changing a running machine.

Ollama 0.33.2 does not authenticate local API clients. Binding to loopback
prevents ordinary remote access but does not distinguish Linux accounts.
Another local account could delete SIA's required model through the API even
when filesystem permissions denied it access to the model files.

The candidate adds a dedicated `inet sia_ollama_owner_v1` nftables table.
Its output hook rejects TCP traffic to loopback port 11434 from a UID other
than the administrator-configured owner; its input hook drops traffic to that
port arriving on another interface. The rule covers the socket, including
model deletion, aliases, copy, pull, and handlers outside Ollama's main router.
It does not depend on an HTTP method, request spelling, Host header or CORS.
Owner requests still encounter all other administrator firewall policies.
The output filter runs at priority 0, after ordinary destination NAT at
priority -100, so an alternate local port redirected to this listener also
encounters the UID check. Administrator rules that rewrite destinations after
the guard are not qualified; privileged firewall changes require revalidation.

The endpoint, pinned binary, model store, GPU settings and owner CLI remain
unchanged. One account owns this host-wide port. This does not add support for
several owners sharing port 11434.

## Administrator boundary

The system service loads the table before login. Every managed Ollama start
runs a gate; the installer runs the same gate before its first mutation.
The gate requires the matching UID, protected root-owned helper/config/unit,
an exact unit definition, no drop-ins or pending daemon reload, and a
successful, active, persistently enabled system service. It then requires a
fresh privileged readback of the complete kernel table. There is no
`SIA_ALLOW_UNPINNED_OLLAMA` exemption.

The root helper creates an absent table in one exclusive nft transaction.
It checks the complete table returned by the kernel. A matching existing
table is accepted; a changed or foreign table is refused without replacement.
It never flushes the host ruleset. Failed creation, malformed output, excessive
output or a deadline prevents success.

Stopping the guard service does **not** delete its table. Uninstalling SIA
leaves Ollama installed, so it also leaves this administrator-owned guard
installed. Removing protection requires stopping every Ollama listener first
and an explicit administrator action.

**Trust assumptions:** the kernel, nftables, systemd, interpreter and root
administrator are trusted. Same-UID code remains outside this account
boundary. A privileged administrator can remove rules, replace executables or
change the service. In particular, a global `nft flush ruleset` can remove the
table while the oneshot service still appears active. Service state alone is
not a live kernel-policy attestation; the startup gate therefore also executes
the narrowly delegated `check-kernel` command. Administrators must preserve this table
across firewall reloads and run `check-kernel` after privileged firewall
changes. The supported firewall lifecycle needs execution evidence before
deployment; do not infer it from unit ordering alone.

This guard also does not guarantee availability against every resource
exhaustion attack or stop another account occupying the port while Ollama is
absent. It does not constrain an owner's model provider or disclosure choices.

## Reviewable installation procedure

This is a proposed manual administrator step, **pending acceptance**. Root
installs one exact sudoers command for the configured UID. It permits only
`/usr/bin/python3 -I -S -B /usr/local/libexec/sia-ollama-guard check-kernel`,
with `NOSETENV` and no argument wildcards. It grants no `apply` command or
general interpreter access. The user installer and startup gate invoke that
fixed check through `sudo -n`; no password prompt or status-only fallback is
allowed. They do not install the delegation or edit firewall policy. The
root checker itself rejects a missing or changed delegation fragment.

Before installation, retain the exact source revision and hashes of
`bin/siaollamaguard.py` and `systemd/sia-ollama-guard.service`. Review the unit
and the rules generated by `rules(uid)`. Inspect existing target paths and the
existing table as administrator. If any target already exists with different
content or ownership, stop and review the upgrade; the following first-install
commands must not be used to overwrite it.

From the reviewed checkout, as the intended ordinary SIA account:

```bash
guard_stage="$(mktemp -d)" || exit 1
chmod 0700 "$guard_stage"
(umask 077; id -u > "$guard_stage/owner") || exit 1
python3 -I -S -B bin/siaollamaguard.py sudoers > "$guard_stage/sudoers" || exit 1
visudo -c -f "$guard_stage/sudoers" || exit 1
sudo install -d -o root -g root -m 0755 /etc/sia /usr/local/libexec
sudo install -o root -g root -m 0644 "$guard_stage/owner" /etc/sia/ollama-owner
sudo install -o root -g root -m 0755 bin/siaollamaguard.py /usr/local/libexec/sia-ollama-guard
sudo install -o root -g root -m 0644 systemd/sia-ollama-guard.service /etc/systemd/system/sia-ollama-guard.service
sudo install -o root -g root -m 0440 "$guard_stage/sudoers" /etc/sudoers.d/sia-ollama-guard
sudo visudo -c
sudo systemctl daemon-reload
sudo systemctl enable --now sia-ollama-guard.service
sudo /usr/bin/python3 -I -S -B /usr/local/libexec/sia-ollama-guard check-kernel
python3 -I -S bin/siaollamaguard.py gate
```

Check every command's result before proceeding. Root installation must verify
the source again after copying and retain the readback hashes. A successful
service start alone does not qualify the installed SIA runtime.
The delegated command must succeed for the configured account, while changed
arguments, `apply`, alternate interpreters and another account must refuse.
Do not infer this authorization test from sudoers syntax validation alone.

For an existing live Ollama, applying the table restricts its current socket
without restarting it. Updating SIA's user unit still needs the normal
lifecycle coordination and an authorized restart. Before accepting the result,
perform a different-account negative probe, an owner embedding, SIA readiness
and recall, reboot/start ordering, and the supported firewall reload test.
Retain failures and compare the actual installed artifacts to the accepted
source. Until these complete, label installed protection **UNPROVEN**.

## Assurance and Power of Ten

Linux performs the client-UID enforcement. This Python helper is an
orchestrator and inspector, not a SPARK-proved authority core. It has closed
subcommands, fixed paths and command arguments, finite byte/time/iteration
limits, no recursion, deliberately checked returns, and explicit refusals.
The interpreter, JSON decoder, allocator, subprocess/kernel behavior and
filesystem durability have not been proved bounded by SPARK. No fixed-memory,
whole-system Power of Ten, avionics or certification claim follows.

The candidate adds reviewable configuration and process tests plus separate
different-UID kernel tests. These distinguish syntax checks, tested behavior,
environmental assumptions, and unrun lifecycle/install evidence. An independent
bypass review and administrator deployment acceptance remain required. This
work does not discharge the continuity kernel, held-out retrieval, recovery,
or full-project GNATprove obligations.
